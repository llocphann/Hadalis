# Hadalis Automation control

The Abyss Settings **Automation** page uses `scripts/hadalis-automation-control.py` as a narrow JSON interface. It stores profile settings at `$XDG_CONFIG_HOME/hadalis/automation.json` and bounded runtime state/history at `$XDG_STATE_HOME/hadalis-automation/manager.json`. The shell settings JSON is not rewritten by the automation daemon, so profile edits cannot overwrite unrelated shell preferences.

The installed `hadalis-chat-bridge.service` runs `python3 -m automation.manager.daemon`. It and the legacy bridge share `chat-bridge.lock`. One profile owns the ChatGPT transport at a time. Other enabled profiles wait by due time and stable list order. A paused owner retains its chat; stopping it releases the queue after any in-flight response completes. Interval runs release their owner after a turn and schedule a later fresh chat. Each profile names an exact ChatGPT Desktop project. Project edits are staged for the next new chat: an already-open or pending chat keeps its captured project name for polling and continuation so an edit cannot redirect an in-flight response. The initially seeded profile starts at `Hadalis Cloud` but is otherwise editable and removable like a custom profile. The manager keeps the original strict-lossless prompt and directive semantics for the built-in profile. New profiles use a general continuation template; edited prompts are wrapped with fixed GitHub, current-dev, ChatGPT-only and no-Work-mode rules.

Profile Start/Resume/Restart starts the installed ChatGPT Desktop, worker and bridge services, then waits for an acknowledgement of that exact command from a fresh scheduler tick. The installed user services may legitimately run from a separate source checkout while Quickshell loads its settings page from a deployed shell directory; different WorkingDirectory values are displayed in diagnostics but never treated as failure by themselves. A stale or outdated bridge without command acknowledgements causes an explicit Start failure and Activity event instead of claiming success. A Start or Restart on an owned session with a stalled pending response explicitly retries observing the *same* baseline, resetting bounded polling errors without resending that prompt. Restart opens a new chat only after that previous response completes. An explicit Start of another profile queues safe handover, lets the previous response finish, and prioritizes the selected profile at the next free transport boundary. Paused owners do not block explicit requests indefinitely. When that previous response cannot be observed because the user has navigated Desktop away from the original project, Settings offers an explicit **Park unresolved previous turn** fallback. The bridge verifies that the original project guard is absent, no ChatGPT generation is active in the current view, and the composer has no draft before releasing transport ownership. Parking preserves the old pending baseline and ChatGPT history, marks that profile `parked_unresolved`, and prevents it from being started again automatically until manual reconciliation; it never clears or resubmits the old prompt.

The periodic health status endpoint is read-only: it surfaces service/heartbeat problems as a separate `scheduler_problem` rather than alternately writing unavailable/recovered states every few seconds. A genuine scheduler tick may record recovery, while failed actions and transport errors remain available in Activity.

Before every submission the driver requires an empty composer and no active Stop control. It also records the count of completed response controls. The manager persists that baseline **before** submitting and accepts only a later completed assistant response with one loop marker. If submission outcome is uncertain, it polls the same baseline and never resends the prompt automatically. Repeated poll errors use bounded backoff and pause after the configured limit. A connector-blocked directive pauses the profile distinctly from a transport error.

Automation Activity can retrieve an on-demand, bounded diagnostics report with profile state, heartbeat, service exit status, recent operational events and the latest matching user-service journal entries. Copy returns the displayed report; export creates a unique mode-0600 log in /tmp. Prompts/config are excluded from the report, but systemd journal entries may contain private information and should be reviewed before sharing. All profiles, including the initially seeded one, use the same local two-step removal confirmation. Active or uncertain chats cannot be removed; a parked unresolved response may be removed because parking already disabled automatic recovery, and removal discards only its local recovery metadata while retaining ChatGPT history. An explicitly empty profile list remains empty until the user creates another profile.

The bridge records only measurable elapsed time, completed turns, sent prompts, failures, job IDs and scheduling times. ChatGPT conversation IDs are not exposed reliably by the current desktop transport. Archive, delete, old-chat cleanup and composer recovery preferences are persisted and clearly marked pending in Settings; they do not act on ChatGPT until a deterministic semantic API exists. No currently active or uncertain chat is cleaned.

Install the services from the source checkout that contains the full Hadalis repository and has a working Git remote, rather than assuming the Quickshell deployment directory is the service source. Update that source checkout before restarting its units; an already-running Python daemon does not reload itself when files are updated. For supported repo-copy installs, run `./setup update --local` from the updated source checkout to synchronize the Quickshell deployment; updating only `~/Hadalis` does not update an independent `~/.config/quickshell/inir` copy. Before restarting a bridge with an uncertain in-flight response, allow it to finish or preserve the state for explicit recovery. Install/reload units with `python3 scripts/install-hadalis-automation.py`. `--reset-session-state` clears the old and managed bridge session state under the shared transport lock while retaining profile configuration. `--enable-now` starts all three user services. `python3 scripts/hadalis-automation-control.py status` prints the same live status snapshot used by Settings.
