### Priority correction: two independent overlap dimensions

The SDK's documented *no remote locking between clients* means the conflict guard must model two different graphs:

- **Local graph**: paths `realpath`/inode when possible, parent/descendant nesting, symlink chains, bind mounts, FUSE mounts, permission/mount changes, and jobs from MEGAcmd as well as independently owned MEGA Desktop. A `realpath` check alone does not prove bind-mount aliases absent.
- **Remote graph**: account identity, actual remote node **handle** where safely available, common ancestor/descendant relationship, inbound shares and links. Two clients on disjoint local paths can still race when aimed at the **same remote destination**. Conversely a remote display path is not an immutable node ID; same-name nodes can coexist and folders move. Missing proof of ownership or remote handle means "unknown", not "safe".

For **new** MEGAcmd sync creation, conservatively require: (1) no overlapping known local subtree/mount; (2) no overlapping known remote folder target under different independently running clients; (3) an explicit warning that *other hosts/accounts* sharing that remote folder cannot be exhaustively discovered by a local app. Do not promise perfect cross-device coordination or block every ordinary intentional multi-device sync; the immediate aim is to prevent unintentionally assigning duplicate local ownership and surface remote race risk. When Desktop data is incomplete, read-only monitoring remains available while mutation is gated to reviewed cases.

## B. Decision record: backend split and precise scope of any future SDK adapter

**B1 — Primary, current direction: existing Rust production workspace + documented MEGAcmd CLI.** Choose for validated vendor-owned sync definitions/status/issue IDs, quota, bandwidth, transfers and backups, with per-installed-version feature probes and fail-closed parser fixtures. Never depend on undocumented MEGAcmd socket framing. A Rust argv vector is necessary but **not sufficient** for exotic names because the vendor reparses arguments as a string internally, as documented in [round 2](CLOUD_STORAGE_MEGACMD_SOURCE_AUDIT.md).

**B2 — Separate, evidence-gated SDK experiment, only if full-fidelity Drive really matters.** The SDK exposes object-oriented methods for nodes/versions and gives a route around CLI human tables/argument reconstruction. There is **no bundled Rust binding** in the examined official repository tree. Options to study are a small isolated C++ bridge communicating typed JSON with the Rust layer, or an audited Rust↔C++ FFI boundary; neither should be added casually to the default shell process. Registration/valid application key is required by the [official SDK source notice](https://github.com/meganz/sdk/blob/74326bb0aa09b13f0a1ec8eab9611e4c0de98cc6/include/mega/megaapp.h). The SDK implementation cannot be assumed to share MEGAcmd's in-memory session, persisted database, cache or running sync engine. **Never extract MEGAcmd's auth session by printing `mega-session` or sharing private configuration files.** If SDK access would require second credential ownership, leave advanced Drive unavailable and ask for explicit design approval.

SDK test questions: Can an isolated *read-only* instance use a separately authorized account without interfering with the CLI client? How much extra RSS, disk cache, network fetch and startup latency does it cost for 10/1,000/100,000 nodes? Is there a safe identity mapping between SDK node handles and current CLI-visible paths across account changes? Does the SDK license/toolchain/package model fit Hadalis's release flows? Never start two sync engines. Only after these checks consider **write** operations and `restoreVersion`.

**B3 — MEGA Desktop optional *presence signal*, not controller.** A Linux filesystem-extension notification server may reveal active local roots for the installed version, but is private, partial and based on extension message framing with newline-delimited paths; unusual filenames or stale/missed notifications make it unsuitable as an authoritative conflict registry. It omits remote sync targets and can be unavailable even while Desktop exists. Any eventual optional detector must be visibly labeled **best effort**, never execute `ExtServer` write-capable commands, and require explicit permission to rely on version-specific vendor internals. Default remains warnings and owner confirmation, not a false green safety badge.

**B4 — Rejected without new vendor guarantee:** directly speaking undocumented MEGAcmd Unix-socket command protocol, reverse-engineering full Desktop configuration state or replacing MEGAcmd's sync scheduler in Rust. These approaches create compatibility, credential and data-loss exposure disproportional to a Settings feature.

## C. Interaction and failure model: avoid irreversible "success" lies

### C1. State representation

A correct UI needs at least three separate clocks: (a) `observation_time` of the server's last confirmed snapshot, (b) `request_time` of the user's action, and (c) `last_successful_reconciliation`. The adapter's `account_epoch` (derived locally from a *nonsecret* identity plus generation; not a persisted session key) invalidates selected items when vendor login/logouts change. Each individual domain stores its **own** freshness; a new quota snapshot does not certify an old transfer list.

State machine: `NOT_INSTALLED → INSTALLED_DISCONNECTED → CONNECT_CONSENT → CONNECTING → {SIGNED_OUT, READY, OFFLINE, DEGRADED}`. Independently, each domain is `NOT_REQUESTED | LOADING | FRESH | STALE | UNSUPPORTED | ERROR`. Mutations: `VALIDATING → AWAITING_USER_CONFIRMATION → DISPATCHING → OUTCOME_UNCERTAIN/ACCEPTED → RECONCILING → CONFIRMED/FAILED/UNKNOWN`. Server process or child exit **does not** imply transfer cancellation or rollback.

### C2. Destructive rename/move and trash recovery

Upstream `moveToDestination` can delete an existing **file** destination after relocating the source, *before* completing its subsequent rename. For Hadalis:

1. The selection must identify a unique source; a destination folder browse or raw destination entry must be resolved afresh.
2. If a destination file or same-name child exists, **reject** rather than use MEGAcmd's replacement semantics. If destination uniqueness is uncertain, disable action.
3. Immediately before dispatch, repeat collision check; external-client races remain possible, so do not promise atomicity. For CLI-only scope with no vendor atomic no-overwrite primitive established, keep high-risk cross-folder move behind an advanced/explicit-risk gate or disabled when strict safety is required.
4. After action, independently inspect source and destination. A move may succeed while rename fails; label `PARTIAL_OR_UNKNOWN`, show what was observed and prohibit automatic retry/cleanup until the user reviews state.
5. `mega-rm` calls the SDK `remove` operation; the exact rubbish-versus-permanent outcome **must be measured** on throwaway objects for this installed version. No unconditional "Recoverable" label. The `//bin` path supports *listing* through source code; manual move-out is a **candidate** but not automatic original-path recovery.

This applies similarly to batch imports, recursive deletes and transfer-cancel-all: postconditions, not optimistic exit messages, drive UI success.

### C3. Secret-handling boundary, with a new negative proof

The examined `MegaCmdExecuter::executecommand` **explicitly rejects noninteractive `login email` without a password**, so neither `printf SECRET | mega-login email` nor Rust's `Command::stdin` can be represented as the official CLI password-entry mechanism at this source revision. The upstream interactive `mega-cmd` shell implements no-echo prompting and conditional history suppression. A future PTY-driven in-page flow would still move secrets through a Hadalis process and MEGAcmd server's internal command string, requiring screen/log/core-dump/redaction and MFA audits. Keep normal QML in read-only signed-out state with "Sign in using MEGAcmd terminal" and vendor-managed existing-session adoption. The upstream [issue #868](https://github.com/meganz/MEGAcmd/issues/868) is an open request asking for non-argv login; it is corroborating context, not the implementation authority.

Secrets prohibited from routine JSON/clipboard/diagnostics: passwords, MFA, `mega-session` strings, restore master key, full exported link fragments/auth-key, proxy credentials, raw stderr or raw long `whoami -l` outputs. For normal dashboard choose `whoami` short form rather than `whoami -l` (which includes session metadata). Review any environment logging flag including `MEGACMD_DO_NOT_REDACT_LINES`; **Hadalis cannot sanitize independently started vendor server logs by launching a sanitized child.**

## D. Runtime/performance and test architecture: more specific than "Rust is faster"

The existing Hadalis [production Rust workspace](../native/Cargo.toml), [native binary installation](../native/scripts/install-runtime.sh), [Arch](../distro/arch/inir-shell/PKGBUILD) and [Nix](../nix/package.nix) packaging make Rust a natural adapter. However external `mega-*` process creation and IPC/network latency may dominate. Because multiple vendor command invocations also register for server state changes, **reduce vendor call count before micro-optimizing JSON**. The adopted design is a **one-shot Rust helper** for bounded reads/commands, not a permanently resident Rust daemon on first release. Add an optional persistent controller only if measured workloads justify it without causing background wakes.

Upstream [Quickshell Process documentation](https://quickshell.org/docs/v0.3.0/types/Quickshell.Io/Process/) describes a tracked child, streams, and lifetime controls. **Verify the installed Quickshell version/API**, then make the Cloud Storage page's Process demand-driven and distinguish killing its *Rust helper* from canceling a *vendor-accepted* transfer/sync action. QML `StdioCollector` can buffer complete helper stdout: the Rust side must also bound serialized **JSON output size and list length**, not just child stdout. For huge folders `mega-ls` has no documented server-side page/limit contract in inspected command docs; displaying the first N rows locally is **not backend pagination**. If data exceeds a safe cap, show explicit truncated/incomplete or require a separately assessed SDK node-browsing layer.

**Visibility lifecycle:** opening the Settings shell alone does not start MEGAcmd; opening Cloud Storage shows static optional-dependency detection; clicking Connect may launch vendor daemon only with explicit consent. If a QML Loader caches a previously visited page, `Component.onCompleted` alone cannot control pollers: all timers and refreshes must track *actual visible page and section* across standalone/overlay/focus and both Abyss/Waffle panel families. Closing Settings suspends Hadalis polling but **never kills the vendor daemon**. On runtime/package upgrades, the adapter must re-probe command capabilities and refuse stale/unknown parse contracts.

### Deterministic local validation, independent of real-account testing

- **Source/adapter unit fixtures**: synthetic server/CLI outputs, explicit column permutations, output truncation, malicious delimiters/newline/quotes, invalid UTF-8, ordinary Vietnamese Unicode, duplicate names, leading dash ID and simulated timeout/broken pipe. These can run offline on synthetic content with a **fake** `mega-*` executable; validate that no dangerous argument is emitted for ambiguous identities.
- **Protocol/model tests**: JSON schema version checks, out-of-order `request_id`, account-epoch invalidation, per-domain freshness, no automatic retry after unknown writes, single-flight write lock and stale error redaction.
- **QML contract tests**: new stable route key, Settings index/migration, category search and section routing, lazy loading, demand-only timers, parent surface variants and error/empty/unsupported/responsive behavior.
- **Exact distro packaging**: when authorized, extend all hardcoded binary enumerations (`native/scripts/install-runtime.sh`, `Makefile`, Arch stable/git and `nix/package.nix`) alongside Cargo workspace source/lockfile; test installed optional binary path and unavailable optional MEGAcmd state. A workspace build passing alone proves **nothing** about installed runtime availability.
- **Separate owner-approved disposable E2E**: installed vendor version/help, local *and remote* collisions, intentional external Desktop ownership, sync issues, backup first-run & retention, transfer race, hang simulation, `//bin` move, normal/inbound-share deletion semantics and SDK read-only coexistence (only if separately approved). These are not safe automatic Local Bot jobs.

### Planned acceptance metrics: require measurements, no invented percentages

For a measured baseline capture distributions (not only averages) of: static-dependency UI opening; Rust CLI startup; vendor CLI spawn; vendor server IPC; queue wait/response; Rust parsing/JSON; QML rendering; memory for 0/100/10,000 node listings; idle Hadalis induced wakeups with feature never opened; active/tab-hidden CPU/RSS, cold signed-out timeout and a deliberately hung *fake* vendor process. Compare equivalent Python implementation only if a tested parity baseline exists. Report both warm and cold results; Rust gains are **hypotheses** until profiled. A background MEGAcmd server may continue by user choice regardless of zero additional Hadalis overhead.
